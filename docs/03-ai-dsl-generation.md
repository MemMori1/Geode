# AI 生成 BinSpec：架构设计

> 前提：已有 `02-dsl-spec-draft.md` 里的 BinSpec 语言。
> 核心命题：**AI 的输出不是聊天文本，是可编译、可执行、可验证的 `.bspec` 源码。**

---

## 0. 一句话设计

> **让模型在一个"有反馈的闭环"里写代码，而不是让模型一次写对。**

单次生成的准确率大概 40~60%（取决于格式知名度）。加上 **验证器 + 3 轮结构化修复**，可以到 85~90%。这个差值就是全部工程量的所在——**verifier 才是产品，模型只是零件**。

---

## 1. 三种交互入口

| 入口 | 用户动作 | AI 任务 |
|---|---|---|
| **A. 一键猜结构** | 打开未知文件，按 `Ctrl+Shift+G` | 从零生成 bspec，覆盖尽可能多的字节 |
| **B. 带意图生成** | "这是 PNG 的一个 chunk，帮我解 IHDR" | 在约束下生成，优先满足用户指明的部分 |
| **C. 增量补全** | 已经手写了一半模板，光标停在空行 | 只补当前上下文（当前 struct 剩余字段 / 下一个 match 分支） |

C 是最容易被低估的——**真实使用里，AI 补 5 行比 AI 生成 200 行有用得多**。它上下文小、延迟低、可验证性强、错误代价低。建议先做 C，再做 A。

## 2. 总体架构

```
 ┌─────────────┐
 │  文件 / 数据源 │
 └──────┬──────┘
        │ ① 智能采样（不是全传！）
        ▼
 ┌──────────────────┐
 │ Context Builder   │──② 熵图 / magic / 用户锚点
 └──────┬───────────┘
        │ ③ prompt + 工具
        ▼
 ┌──────────────────┐   ④ 结构化输出（grammar-constrained）
 │   LLM (本地/云端)  │◄──────────────────────────────┐
 └──────┬───────────┘                                  │
        │ bspec 源码                                    │
        ▼                                              │
 ┌──────────────────┐   ⑤ 编译错误 / 运行诊断 / 不变量失败 │
 │     Verifier      │──────────────────────────────────┘
 │  编译→执行→自检    │        最多 3 轮修复
 └──────┬───────────┘
        │ ⑥ 打分 + 每字段置信度
        ▼
 ┌──────────────────┐
 │  渐进式 UI 呈现    │──⑦ 用户修正 → 回灌为 few-shot
 └──────────────────┘
```

## 3. ① 智能采样：整个系统的成本命门

1GB 文件不能全给模型。但**盲目取前 4KB 会毁掉一切**——很多格式的关键结构在尾部（ZIP 的 EOCD、PE 的 section table、MP4 的 moov）。

### 3.1 采样策略（分层，总计 32~64KB）

| 层 | 位置 | 大小 | 理由 |
|---|---|---|---|
| L1 头 | `[0, 4KB)` | 4KB | magic / 文件头必在此 |
| L2 尾 | `[size-4KB, size)` | 4KB | trailer / 索引 / 目录表 |
| L3 熵谷 | 滑动窗口熵最低的 16 个 512B 区 | 8KB | **结构区通常低熵，数据区高熵** |
| L4 对数间隔 | 按 `size * 2^-k` 取 16 片 × 256B | 4KB | 保证长度尺度上的覆盖（小结构 vs 大块） |
| L5 用户锚点 | 用户框选/光标处 ±1KB | 2KB | 用户意图优先 |
| L6 magic 命中 | `magic` 库匹配位置 ±256B | 1KB | 若识别为已知格式，确认版本差异 |

**L3 是这个设计里最漂亮的一手**：对二进制做 512 字节滑窗 Shannon 熵，**取熵最低的区段**。压缩/加密/图像数据熵接近 8.0，而头部、目录、长度表熵通常在 3~5。这个启发式几乎免费，却让采样命中率大幅提高。同理，**熵图本身也是极好的 prompt 素材**（"文件分为 3 个高熵区和 2 个低熵区，边界在 X/Y/Z"）。

### 3.2 Agentic 采样（模型主动要数据）

采样只是初值。模型可以在循环里调工具要更多数据：

```json
{"tool": "read", "args": {"offset": 12345, "len": 512}}
{"tool": "entropy_map", "args": {"window": 4096}}
{"tool": "find", "args": {"pattern": "50 4B 03 04", "limit": 10}}
{"tool": "template_search", "args": {"query": "zip local file header"}}
{"tool": "compile", "args": {"spec": "..."}}
{"tool": "run", "args": {"spec": "...", "entry": "0x0"}}
```

**关键**：`compile` / `run` 是工具，不是后处理。模型能自己编译、自己看报错、自己改。这就是把 verifier 塞进 agentic loop。

工具调用次数上限（默认 24 次）、读取字节上限（默认 2MB）、总时长上限（默认 90s）——防止 agent 无限探索。

## 4. ② 上下文构造

### 4.1 Prompt 结构

```
[system]
  你是一个二进制格式分析引擎。输出 BinSpec 源码。
  ── 语言规范摘要（~2KB，压缩版语法 + 5 个例子）
  ── 输出约束：只输出 <spec>...</spec>，禁止解释
  ── 硬规则：
     1. 不要发明 magic。任何一个 signature 字段的初值都必须来自实际读到的字节。
     2. 你能读到多少字节，就只声明多少字段。不确定的地方写 u8 unknown_N[size]。
     3. 每个 struct 结尾必须能到达一个明确的边界（EOF / 尾部锚点 / 长度字段）。
     4. 不确定的字段名用 field_0xNN，不要编造语义名。

[context]
  ── 文件元信息：name, size, sha256, 熵统计, 检测到的类型(若有)
  ── 采样切片（带偏移标注）
        @0x0000 (256B)
        00000000  89 50 4E 47 0D 0A 1A 0A 00 00 00 0D 49 48 44 52 ...
        @0x0020 (256B)
        ...
  ── 相邻结构重复性提示：签名 "50 4B 03 04" 出现 47 次，平均间隔 512B
  ── RAG 检索到的相似模板（若有，最多 2 个）

[task]
  生成完整 bspec，最大化字节覆盖率与字段正确性。
```

### 4.2 结构化输出：grammar-constrained decoding

**这是最强的单点杠杆。** 用 GBNF / JSON-Schema-derived grammar 把解码约束在 BinSpec 语法内：

- 语法错误率从 ~15% 降到 ~0
- 不会输出 Markdown 包裹、前言后语
- 不会编造不存在的关键字

实现：llama.cpp `GBNF`、vLLM `guided_decoding`、OpenAI `json_schema`/`grammar`、或本地运行的 `outlines` 库。

注意：**约束解码只保证"语法合法"，不保证"语义正确"**。verifier 不可省。

### 4.3 RAG：模板库既是产品也是语料

用户社区积累的 bspec 模板 = 检索语料。
- 索引：magic 字节 + 文件类型名 + 结构描述 embedding
- 检索：先按 magic 精确匹配（强信号），再按语义 embedding 召回
- 注入：最多 2 个模板，每个截断到 80 行（只注入 struct 骨架，不注入具体字段值）

这带来一个正循环：**用得越多 → 模板库越大 → 生成越准 → 用得越多**。这也是为什么模板库要从第一天就开始攒。

## 5. ⑤ Verifier：核心资产

### 5.1 三层验证

```
L1 编译   语法 / 类型 / 未定义符号 → E4xxx
L2 执行   在真实文件上跑 → 运行诊断 E1xxx / E3xxx / 预算 E2xxx
L3 不变量 结构合理性自检（下面这张表）
```

### 5.2 不变量清单（自动可判定）

| ID | 不变量 | 检查方法 | 权重 |
|---|---|---|---|
| I1 | 编译通过 | 编译器 | 硬门槛 |
| I2 | 所有读取在文件边界内 | VM 边界检查 | 硬门槛 |
| I3 | 重复结构真的重复 | 采样切片里签名出现次数 ≥ 2 且间隔一致 | 高 |
| I4 | 字节覆盖率 ≥ 阈值 | `sum(顶层 unit 覆盖字节) / file_size`；<40% 视为不合格 | 高 |
| I5 | 长度字段自洽 | `length == 子结构实际消费字节`，或 `offset[i+1] - offset[i] == size[i]` | 高 |
| I6 | 结构闭合 | 解析结束时游标 ∈ {EOF, 已知尾部锚点}，误差 < 64B | 高 |
| I7 | 数组元素数合理 | `1 ≤ count ≤ 1e6` 且与文件大小自洽 | 中 |
| I8 | 断言通过 | `#[assert]` 全过 | 中 |
| I9 | 偏移单调（无 `@` 时） | 顺序读的 offset 严格递增 | 中 |
| I10 | 无未读区段 | 顶层 unit 之间无 > 1KB 的空洞 | 低 |

分数：`score = Σ(weight_i * passed_i)`，I1/I2 不通过直接 0 分。

### 5.3 Best-of-N + Verifier 排序

```
N = 4（云端）/ 8（本地小模型，便宜）
for each candidate: compile → run → score
选 score 最高者进入修复循环
```

经验上 best-of-4 + verifier 比 best-of-1 准确率提升 20~30 个百分点，是**性价比最高的一招**。它把"模型的方差"变成了"我们的收益"。

## 6. ⑥ 修复循环

最多 3 轮。每轮的输入是**最小必要信息**：

```json
{
  "previous_spec": "<只给出错 unit 的源码片段，不是全文>",
  "diagnostics": [ {code, offset, length, expected, actual, path, suggestion} ],
  "bytes_at_error": "@0x1A20 (32B)\n00001A20  00 00 00 00 00 00 00 00 ...",
  "instruction": "只重新输出 struct Xxx { ... }; 这一段，其他部分不要输出。"
}
```

设计要点：
- **只重写出错段落**，不是整份 spec。否则每轮都会引入新错误（LLM 的"重写退化"效应）
- **错误上下文窗口** = 出错偏移前后 32 字节的真实 hexdump。模型看到实际字节后的修复率显著高于只看报错文字
- **加入"已验证正确"的段落作为锚**（"以下部分已验证通过，不要改动：..."）
- 3 轮仍失败 → 降级：输出"部分成功"结果 + 明确列出无法解析的区域，**不要给用户一个跑不通的模板**

## 7. ⑦ 置信度模型

每个字段带 `conf ∈ [0,1]`，写进 `#[ai:conf(...)]`。来源：

| 信号 | 增量 | 说明 |
|---|---|---|
| magic 命中已知库 | 基线 0.95 | 几乎确定 |
| 用户框选并标注过该区域 | → 1.0 | 人工确认 |
| 长度/偏移字段自洽（I5 通过） | +0.15 | 结构自证 |
| 在 ≥3 个采样切片上重复一致（I3） | +0.15 | 跨样本验证 |
| 有 `#[assert]` 且通过 | +0.05 | |
| 仅由模型自评（无任何外部验证） | 上限 0.45 | **刻意压低** |
| 落在未采样区域 | 上限 0.30 | 模型没见过，纯猜 |
| 该字段读取时出现 unresolvable | 0.0 | |

**呈现**（这是体验的分水岭）：

```
结构树                               hex 视图背景
▼ ZipArchive                                   
  ▼ ZipLocalHeader first      0.98  ┤ ████ 深绿：确定
      signature               1.00  │
      versionNeeded           0.85  │
      method                  0.82  │
  ▼ ZipLocalHeader rest[47]   0.71  ┤ ███ 浅绿：较可信
      ...
  ▼ unknown_0x1A20            0.30  ┤ ███ 灰：猜的
```

- 深绿 = 有 magic/断言/跨样本支撑
- 黄 = 结构自洽但语义未验证（"这里是个 u32，但不知道它是什么"）
- 灰 = 纯占位（应该显式显示为 `unknown_0xNN`，而不是编个假名字）
- **允许用户点击改置信度**：右键 → "这个猜错了" → 该修正作为负样本回灌 prompt 缓存 + 进入个人 few-shot 库

> **产品原则：宁可承认不知道，也不要编造。** 一个诚实的 40% 覆盖率 + 灰区，远好于一个看起来很完整但字段名全是幻觉的模板。

## 8. 渐进式呈现（延迟预算）

用户按 `Ctrl+Shift+G` 后的体验：

| 时刻 | 出现什么 |
|---|---|
| 0ms | 进入"分析中"，hex 视图可继续滚动 |
| ~300ms | 采样完成，显示"已识别 3 个候选格式"（本地 magic + 小模型快速分类） |
| ~2s（本地 7B）/ ~6s（云端） | 第一版结构树出现（**流式 token，边收边解析已完成的 struct**） |
| 后台 | 修复循环 + best-of-N 静默进行，结构树逐步"变绿" |
| 用户随时可 | 取消 / 采纳 / 手动编辑（编辑后 AI 停止，或进入模式 C 补全） |

**流式渲染很关键**：不等完整 spec，每收到一个闭合的 `struct {...};` 就编译并上屏。体验上从"等 6 秒"变成"1 秒后不断长出来"。

## 9. AI 的其它落点（不必一次做完，但共用同一套基础设施）

| 功能 | 输入 | 输出 | 难度 |
|---|---|---|---|
| **字段命名/注释** | 已跑通的模板 + 字节 | 把 `field_0x1C` 改成 `crc32Checksum` | 低（高价值） |
| **报错解释** | 诊断 JSON | "这里期望 4 字节但只剩 2 字节，因为你前面的数组长度字段把 padding 也算进去了" | 低（高价值） |
| **自然语言查询** | "找出所有指向字符串表的指针" | bspec + 执行 → 结果列表 | 中 |
| **C/Rust struct → bspec** | 头文件源码 | bspec | 低（几乎无损） |
| **Kaitai .ksy → bspec** | .ksy | bspec | 低（迁移工具，抢 Kaitai 用户） |
| **Diff 解释** | 两份数据 + 结构 | "偏移 0x400 处的调色板索引被改过" | 中 |
| **测试样本生成** | bspec | 合成一个最小的合法文件（用于验证） | 中（沙箱执行要写能力） |
| **格式猜测（magic 库外）** | 采样 + 熵图 | 格式候选清单 + 理由 | 中 |

**优先顺序建议**：字段命名 ≥ 报错解释 > C struct 转换 > 一键猜结构 > 其余。
理由：前两个是**在已有正确结果上锦上添花**，出错代价极低，用户感知强。一键猜结构虽然炫，但出错代价高，适合后置。

## 10. 隐私与部署

逆向的输入常有强隐私属性（私有固件、客户数据、恶意样本）。

- **默认本地**：打包 7B~14B 量化模型（4~8GB），走 llama.cpp。准确率低一档，但零外传
- **云端可选**：用户显式开启，且发送前展示"将要发送的采样预览"（可逐片剔除）
- **分级隐私模式**：
  - `strict`：全本地，不发任何字节（**默认**；19 §8 已裁决，项目文件不得下调）
  - `balanced`：只发采样切片（需用户显式选择）
  - `permissive`：允许 agent 主动读取任意区域
- **不发整文件**，这是硬约束（内置防呆：单次上传字节数上限 + 累计上限提示）
- **provenance 记录**：每个生成的模板记录 `{model, prompt_hash, sample_hash, ts}`，可复现、可审计
- 企业版：本地模型 + 私有模板库，完全离线

> 有意思的折中：**"本地起草 + 云端只审"**——本地小模型产出 spec 和诊断，云端大模型只看 spec + 诊断（不含原始字节）判断"哪里可能不对"。既省 token 又减少隐私暴露。可作为一个可选模式。

## 11. 评测集（不做这个，AI 功能就是玄学）

### 11.1 Benchmark 构成

20~30 个格式，每类都要有：
- 真实样本文件（2~3 个版本，覆盖版本差异）
- ground truth 结构（**从 Kaitai Struct 已有的 `.ksy` 半自动转换**，人工校对）

覆盖建议：PNG、JPEG、GIF、BMP、WAV、MP3(ID3)、FLAC、MP4(ISO BMFF)、ZIP、GZIP、TAR、7z、ELF32/64、PE、Mach-O、SQLite、TrueType/OTF、Protobuf(wire)、MessagePack、CBOR、PCAP、Bencode、DER/ASN.1、RIFF、TIFF、ICO、PDF。

### 11.2 指标

| 指标 | 定义 | 目标（v1） |
|---|---|---|
| `compile@1` | 一次生成就编译通过 | > 85% |
| `run@1` | 一次生成就无运行期错误 | > 55% |
| `run@3` | 3 轮修复后跑通 | > 88% |
| `byte_coverage` | 顶层 unit 覆盖字节 / 文件大小 | > 75% |
| `field_precision` | 字段偏移正确的比例 | > 80% |
| `field_semantic` | 字段名语义正确（人工/LLM-as-judge） | > 50% |
| `hallucination_rate` | 声明了但实际不存在的字段 / 总字段 | < 3% |
| `cost/次` | token 成本 | < $0.15 |
| `p50 latency` | 首次上屏 | < 3s（本地）/ < 7s（云端） |

### 11.3 回归

模型升级 / prompt 改动 / 语法演进，每次都跑全量。**这是唯一能防止"悄悄变差"的手段。**

## 12. 风险与护栏

| 风险 | 护栏 |
|---|---|
| **幻觉字段**（编造不存在的 magic/字段） | 每个字段必须能回链到真实字节区间；回链失败直接丢弃并降级为 `unknown_0xNN`。硬约束，不可配置 |
| **过拟合采样**（只看到前 4KB 就断言数组长度） | 跨样本一致性检查（I3）+ 未采样区的字段强制 conf ≤ 0.30 |
| **模型编造语义名**（把 checksum 叫成 timestamp） | system prompt 硬规则 + 命名只在 verifier 通过后由第二个小任务生成；高风险的语义名默认不加，用户可一键"帮我命名" |
| **成本失控** | best-of-N 可配（默认 4）、修复轮数上限 3、工具调用上限 24、单文件 token 上限、会话总预算、UI 显示已消耗 |
| **延迟过长** | 流式渲染 + 本地快速分类先出结果 + 允许"先给我粗的，后台精修" |
| **隐私泄漏** | 默认本地；发送前预览；字节上限硬约束 |
| **模型/版本漂移** | 固定 prompt 版本 + eval 回归 + 缓存 prompt_hash |
| **AI 依赖成瘾**（用户不会手写模板了） | 生成的 bspec 始终是**可读、可编辑的源码**（不是不透明的中间产物）；提供"解释这段模板"功能 |
| **恶意文件攻击解析器** | 沙箱预算（DSL spec §7.2）+ Rust 实现 + fuzz 测试 |

## 13. 落地顺序（建议）

| 阶段 | 内容 | 依赖 | 工期 |
|---|---|---|---|
| **A0** | 语法 finalized + 编译器/VM + 诊断 JSON（DSL spec §7/§8） | DSL 实现 | —— |
| **A1** | **Verifier 单独成模块**，可脱离 AI 使用（手工模板的 lint/校验也是它） | A0 | 1 周 |
| **A2** | 模式 C：增量补全（上下文小、可验证、延迟低） | A0+A1 | 2~3 周 |
| **A3** | 字段命名 + 报错解释（低风险高感知） | A0+A1 | 1 周 |
| **A4** | 采样器（含熵谷策略）+ 上下文构造 + 结构化输出约束 | 无 | 2 周 |
| **A5** | 模式 A/B：完整生成 + best-of-N + 修复循环 | A1+A4 | 3~4 周 |
| **A6** | 置信度模型 + 渐进式 UI + 修正回灌 | A5 | 2 周 |
| **A7** | Eval benchmark + 回归 CI | A5 | 2 周 |
| **A8** | 本地模型打包 + 隐私模式 | 全 | 2 周 |

**关键判断：A1（verifier）必须先于 AI 存在。** 它不依赖模型，且对"手工写模板"的用户同样有巨大价值（相当于模板的 type checker + linter）。先做它，AI 才有落脚点。

---

## 14. 一个诚实的判断

AI 生成模板这件事，**在"知名格式"上会显得非常神奇**（模型见过成百上千个 PNG 模板），**在"私有/自研格式"上会显得很笨**（它只能靠字节模式猜）。

所以产品的真实定位应该是：

> **AI 不是替你做逆向，是替你做 80% 的机械劳动（读字段、算偏移、写样板），剩下 20% 的判断（这个字段到底是啥意思）永远是你的。**

对应到设计上：
- **对已知格式**：追求高覆盖率 + 高置信度，一键出结果
- **对未知格式**：追求"骨架正确 + 语义留白"，快速给出可编辑的初稿，让用户在 10 分钟内把 200 行样板改完，而不是 2 小时

这个定位不吹牛，但确实能省掉逆向工程师大量时间——而且不会因为"AI 猜错了"而挨骂。

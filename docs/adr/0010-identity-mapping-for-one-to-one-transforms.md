# 0010 — 1:1 变换退化为 Identity 映射 + 组内置换

## 状态

已接受（2026-11-08）

## 背景

数据处理器图要在 100GB 级视图上做到"滚动无额外延迟"。若每类变换都建索引，索引内存与构建时间会随视图大小线性增长；而 XOR、位反转、字节序翻转、半字节交换、ROT 这类变换的共同点是**保长且偏移恒等**：`src_off == view_off`。原设计容易把字节序翻转当成 N:1 变换处理（因为它"重排了字节"），实际它是 1:1 的组内置换。索引上限 `index_max_entries = 262144`（≈ 8MB，约 16GB 输出），超出后 `stride *= 4` 转稀疏锚点。见 07 §1.2、07 §4.1、07 §4.4。

## 决策

凡 `caps.len_preserving && src_off == view_off` 的 1:1 变换，一律退化为 `map_range(v) = [(Root, v)]`、`quality = Identity`、`unmap` 恒等，真正变换只在 `transform_block` 中按组做 `permute(buf, group_off)`。

## 后果

**好处**
- 零索引内存、零构建时间、随机读 O(1)，unmap 精确——这是"1GB 视图滚动无额外延迟"的全部原因（见 07 §4.1）。
- 偏移恒等使字节级 patch、光标定位、选区在视图与源之间无需映射表，编辑路径的语义大幅简化。
- 只有非保长或重排型变换才需要建索引，索引预算（262144 条）能覆盖更"值得建索引"的场景。
- 组内置换按组读对齐字节再重排，缓存友好且可向量化。

**代价**
- 每类变换必须显式声明"是否偏移恒等"，声明错了会静默产生错位结果（字节序翻转最易误标为 N:1）。
- 视图内编辑只在 `MapQuality::Identity | Exact` 且全链 `reversible` 时开放，1:1 之外的链条一律只读（如 CBC 需重加密整块）。
- 组边界（如 4 字节/8 字节组）与块读边界（64KiB）不对齐时仍需小心处理尾部。

**待澄清**
- 07 §4.1 未列出 `group_size` 与图节点声明字段的最终形态（是图级配置还是节点级），也未说明嵌套 1:1 变换（如 XOR 后再字节序翻转）是否合并为单一置换；需作者确认后再固化。

**何时应重新考虑**
- 若出现"保长但非偏移恒等"的高频变换（如块内转置 8×8），Identity 退化不成立，需要重新定义 fast path。
- 若索引预算被证明过于保守或过于宽松（262144 条的实测命中分布偏离预期）。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 所有变换统一建索引 | 1:1 场景下白付 O(view) 内存与构建时间，与"1GB 视图滚动零额外延迟"冲突 |
| 把字节序翻转当 N:1 处理 | 它是 1:1 组置换，按 N:1 建模会丢精度、增大索引且 unmap 不精确（见 07 §4.1） |
| 变换只在输出端整体重算 | 100GB 不可行，违反 C1（UI 路径不得 O(文件大小)） |
| 允许对任意图反算以支持编辑 | CBC 等需重加密整块，无法廉价反算；编辑开放条件收紧到 Identity/Exact 是可承受的代价（见 07 §1.2） |

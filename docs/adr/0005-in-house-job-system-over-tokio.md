# 0005 — 自研 job 系统（crossbeam-channel + rayon）而非 tokio

## 状态

已接受（2026-11-08）

## 背景

系统的所有后台工作都是 **CPU-bound 批处理**：100GB 文件的流式搜索（> 800MB/s）、diff（两个 100MB < 5s）、YARA 流式扫描（≥ 35MB/s）、BinSpec 执行、内容索引解析。硬约束有两条：UI 线程不得做 **> 1ms** 的工作；任何后台任务必须在 **100ms** 内响应 `CancelToken`。产物通过 `UiEvent` 通道每帧 drain 一次回主线程，且回主线程时必须校验 `buffer.version()`。见 00 §2、00 §6。

## 决策

采用自研轻量 job 系统：`crossbeam-channel` 传递任务与事件、`rayon` 线程池执行，**不引入 tokio**。

## 后果

**好处**
- 与工作负载同构：rayon 的 work-stealing 天然适配"按块 `par_iter` + 协作式取消"（见 08 §4.5、09 §4.1）。
- 没有 async 运行时，也就没有 `Send`/生命周期/Send-across-await 的传染成本，内核 crate 保持同步签名。
- 取消与预算是显式参数（`JobCtx` 提供 cancel/progress/预算），可测试、可注入。
- 网络请求也能容纳：内容分发用阻塞 `ureq` 跑在 job 线程即可（见 15 §2）。

**代价**
- 大量并发 I/O（如同时拉多个远端内容的进度流）需要自己编排线程而非 `select!`；一旦出现真正的异步 I/O 密集场景，改造成本高。
- 任务取消是协作式的，粒度为"每 N 次迭代检查"，长循环忘记检查就会突破 100ms 预算。
- 没有现成的超时/timer 设施，须由 job 自己实现（如 Provider 读超时 5s）。

**待澄清**
- 00 §2 只给了一条否决理由（"tokio 只增加复杂度"），未说明"什么条件下允许引入局部异步运行时"；若将来出现原生 async 的必需依赖（如某些 SSH 库），需先补这条裁决。

**何时应重新考虑**
- 出现无法绕开的 async-only 关键依赖（SSH/GDB 远端源的成熟库多为 async）。
- 后台任务从"批处理"变为"长期多路流复用"（如同时监视 10 个 volatile 源的变更）。
- 若 `ureq` 式的阻塞 I/O 在 SMB/网络盘上造成线程堆积而非 CPU 饱和。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| tokio 全量 | 本系统全是 CPU-bound 批处理，无大量异步 I/O，tokio 只增加复杂度（见 00 §2） |
| 纯 `std::thread` + 手写池 | 无 work-stealing，100GB 场景下的分块并行会因负载不均而空转 |
| rayon 单一图（无 channel） | 缺少 UI↔job 的解耦边界；UI 每帧 drain 需要一个通道，且要能丢弃陈旧结果 |
| 每个子系统自建线程 | 与"统一分块缓存"同理：N 套实现 = N 套 bug（见 06 §1.3） |

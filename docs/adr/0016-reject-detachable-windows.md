# 0016 — 否决可分离独立窗口（detach）

## 状态

已否决（2026-11-08）

## 背景

需求是"把某个面板拖成独立窗口，放到第二块显示器上对照"。egui 提供多 viewport 能力，看起来是低成本特性；但三条平台级问题无法在应用层绕开：**焦点回传**（子窗口获焦时主窗口丢一帧 input，命令与快捷键需要额外仲裁）、**DPI 迁移**（窗口拖到不同缩放比显示器时 `pixels_per_point` 变化会让已缓存的字形图集与度量失效并需重建，重复重建会闪）、**IME**（多 viewport 下 CJK 候选窗锚点错位是 egui 已知问题，直接影响中文用户）。收益侧：同窗口内水平拆分已满足约 **90%** 的对照需求。见 16 §4.1。

## 决策

**不做**可分离独立窗口（detach），面板只能在主窗口内停靠与拆分。

## 后果

**好处**
- 避开三条平台级坑：无需实现命令/快捷键的跨窗口仲裁，无字形图集重复重建的闪烁，CJK 候选窗锚点保持正确。
- 单一 viewport ⇒ 单一 `pixels_per_point` ⇒ 字形图集、度量缓存、布局刻度全部只有一份，渲染预算（≤ 8 draw call）不被翻倍。
- 布局持久化与命令分发（菜单/工具栏/命令面板共用 `CommandId`）保持单一路径，见 16 §4.2。

**代价**
- 双显示器对照只能靠"窗口拉宽 + 水平拆分"或开两个应用实例，做不到真正的独立窗口平铺。
- 若将来必须支持 detach，改动面不止 UI：字体图集、输入路由、命令仲裁、IME 都要重做。

**保留后路**
- `ShellLayout` 预留 `detached: HashSet<PanelId>` 字段（**恒空、不序列化**），确保未来加该特性时不需要破坏性格式迁移。

**何时应重新考虑**
- egui 的多 viewport 焦点回传与 IME 锚点在三大平台都稳定，且 DPI 迁移重建能做到无闪烁时。
- 用户调研显示"必须独立窗口"是弃用原因（而非只是加分项）。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 用 egui viewport 做 detach | 焦点回传不可靠（子窗口获焦时主窗口丢一帧 input，命令与快捷键需额外仲裁） |
| detach + 每窗口独立 DPI 处理 | `pixels_per_point` 变化使字形图集与度量缓存失效需重建，重复重建会闪 |
| detach 但禁用 IME | 直接损害中文等 CJK 用户，不可接受的降级 |
| 开第二个进程共享同一文件 | 双实例的编辑冲突与 journal 归属复杂（见 17 §4.6），远超"对照"需求 |
| 主窗口内水平/垂直拆分 | **采纳**：满足约 90% 的对照需求，成本几乎为零 |

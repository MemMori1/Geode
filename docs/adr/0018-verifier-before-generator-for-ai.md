# 0018 — AI 能力按"verifier 先于生成器"的顺序落地

## 状态

已接受（2026-11-08）

## 背景

模型单次生成 BinSpec 的准确率只有 **40~60%**，加上 verifier 与 3 轮修复可提升到 **85~90%**；原文的判断是"verifier 才是产品，模型只是零件"（见 03 §0）。这让落地顺序成为一个架构问题而非排期问题：若先做生成器，产品在 verifier 出现前会长期处于"看起来能用但错得静默"的状态，且没有可量化的评估基线。v1 质量指标要求 `run@1 > 55%`、`run@3 > 88%`、`field_precision > 80%`、`hallucination_rate < 3%`（见 03 §11.2）。

## 决策

按 A0→A1→A2…顺序落地，且 **A1（Verifier）必须先于任何 AI 生成能力存在**，并作为可脱离 AI 独立使用的模块交付。

顺序：A0 语法 + 编译器/VM + 诊断 → **A1 Verifier 单独成模块（约 1 周）** → A2 增量补全（2~3 周）→ A3 命名与报错解释（1 周）→ A4 采样器（2 周）→ A5 完整生成 + best-of-N + 修复循环（3~4 周）→ A6 置信度与渐进 UI → A7 eval 回归 → A8 本地模型。

## 后果

**好处**
- Verifier 可以脱离 AI 独立交付，立刻给手写模板的用户带来价值（相当于 type checker + linter），因此它不依赖任何模型可用性。
- 生成侧的所有护栏有统一的落地位置：幻觉字段必须回链真实字节，否则降级为 `unknown_0xNN`（硬约束）；`best-of-N` 默认 **4**、修复轮数上限 **3**、工具调用上限 **24**。
- 有了可量化的评估基线（03 §11.2 的九项指标），模型/提示词替换变成可回归的工程动作而非感觉判断。
- 采样器（A4，分层 32~64KB）与 Verifier 独立，二者可分别优化。

**代价**
- 前 1 周没有任何"AI 功能"可演示，排期上会被误读为进度慢。
- Verifier 必须覆盖到与 VM 语义一致的细节（`unresolvable` 越界不是硬错误、`@` 不移动游标等），否则它会否掉正确的模板——误报比漏报更伤信任。
- best-of-N 与修复循环带来成本与延迟压力：目标 `cost < 0.15 美元`、`p50 latency < 3s`（本地）/`< 7s`（云端）。

**待澄清**
- 03 §13 的 A2 步骤写的是"增补全"（增量补全），与 §1 三入口（A 一键猜结构 / B 带意图生成 / C 增量补全）的字母编号 A/B/C 重名，易混；A1 与 A2 之间的依赖是否强制（A2 是否必须复用 verifier 的诊断通道）原文未明确。

**何时应重新考虑**
- 若出现基础模型在 BinSpec 上的 `compile@1` 已稳定 > 85%，修复循环与 best-of-N 的必要性下降，顺序可压缩。
- 若 Verifier 的误报率持续偏高，应先修 Verifier 而不是继续推进生成侧。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 先做生成器，后补 verifier | 单次准确率仅 40~60%，没有 verifier 就没有可行性与幻觉护栏，产品处于静默出错状态（见 03 §0、03 §13） |
| 生成与 verifier 并行开发 | 生成侧的输出契约会随 verifier 演进而反复变动；先定 verifier 等于先定契约 |
| 直接依赖外部 DSL 校验器 | BinSpec 的语义（`unresolvable` 越界、`@` 不移动游标、预算）无处可借，校验器必须内生 |
| 先做 A（一键猜结构） | 原文建议先做 C（增量补全）：输入更局部、上下文更确定、用户可即时判断对错 |

# 0003 — 技术栈定为 Rust + egui + wgpu

## 状态

已接受（2026-11-08）

## 背景

Hex 工具的核心风险面是"解析不可信二进制 + 执行用户规则/脚本"，这决定了语言选择；而 hex 网格一屏约 **4000 个单元格**、文件可达 **100GB**，决定了 GUI 必须是自绘而非控件树。语言对比中 Rust 的内存安全 ★★★★★、C++ ★★；GUI 生态 Rust ★★★、C++/Qt ★★★★★（见 01 §5）。选型结论同时受一条硬约束约束：除 `geode-ui` 与 `app` 外任何 crate 不得依赖 GUI 库（见 00 §2），因此 GUI 框架必须是"可被隔离在下游"的。

## 决策

采用 **Rust（edition 2024）+ egui（立即模式）+ wgpu 后端**，hex 网格用 `Painter` 自绘（走 wgpu paint callback），不用 widget 树。

## 后果

**好处**
- 把 `unsafe` 收敛到 mmap 那一小块与 FFI 边界，性价比最高（见 01 §5）。
- 立即模式 + 自绘天然满足"每帧只画可见行（40~80 行，硬上限 96）"，与 `doc_len` 无关（见 05 §1.1）。
- 一屏 ~4000 单元格用 Painter 自绘 + 字形图集，可压到 ≤ 8 draw call；任何 retained widget 都会崩（见 00 §2、05 §4.3）。
- 核心 crate 不存在 `egui`/`wgpu` 依赖，未来换 UI 框架不动内核（见 01 §5 建议）。

**代价**
- 表格/文本选择交互要自己写；CJK 字体需手动加载；无原生控件观感（见 01 §5）。
- 偏移列/hex 列不能走文本整形，须自建字形图集路径（见 05 §4.3）。
- egui 生态版本变动会影响自绘细节，需锁定版本并在 CI 五目标上验证。

**何时应重新考虑**
- 若产品需要原生控件观感与系统级集成（macOS 菜单栏、Windows 触控惯性），Qt 的收益会压过自绘灵活性。
- 若出现"Web 版必须复用"的真实需求且大文件 IPC 方案可解，可重估 Tauri 前端 + Rust 内核。
- 若 egui 的自绘能力成为瓶颈（而非数据层），可按 01 §5 的建议只换 UI 层。

**待澄清**
- 00 §2 的备选栏只覆盖 C++、Qt、Tauri+Web，`GPUI` 一项无原文比较依据；本 ADR 对其的否决理由（同为 retained/自有渲染栈、生态锁定、缺少大文件自绘先例）是按上述不变量推导的，需原文档作者确认。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| C++（+ Qt6 自绘） | 解析不可信二进制 + 执行用户脚本是 C++ 的死亡地带，每年都有工具被恶意样本打穿；Qt 另有包体积 + LGPL 动态链接约束，且自绘 hex 视图并无优势（见 00 §2、01 §5） |
| Electron / Tauri+Web | hex 视图仍必须 canvas 自绘，大文件数据经 IPC 有成本，Web 化收益不抵复杂度（见 00 §2） |
| GPUI | 见上方「待澄清」：按同类 retained-生态问题否决，非原文裁决 |
| iced / Slint | 保留式架构更清晰，但 hex 视图这种自定义自绘场景收益不大（见 01 §5） |
| Flutter | 桌面生态弱，文本选择/输入法在桌面端仍有坑（见 01 §5） |

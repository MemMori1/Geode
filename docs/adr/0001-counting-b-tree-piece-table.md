# 0001 — piece 容器采用计数型 B-tree

## 状态

已接受（2026-11-08）

## 背景

Geode 的 Buffer 要在 100GB 级文件上承载 10⁴~10⁶ 次编辑，定位与插删必须与文件大小无关（C1，见 00 §1）。候选容器在真实规模下是量级差：扇出 64 时树高 ⌈log₆₄ 10⁶⌉ = 4，而二叉树是 log₂ ≈ 20；定位 = 4 次指针跳 + 叶内扫 64 个累计长度（SIMD 友好）≈ 200ns，二叉树 20 次指针追逐 ≈ 1.5µs。piece 描述子固定 32B，任何"每片额外开销"都要乘 100 万。见 04 §3.1。

## 决策

采用**计数型 B-tree**（fanout 64、每叶 64 piece、叶装载率下限 25%）作为唯一 piece 容器。

## 后果

**好处**
- 定位/插删 O(log N)，支撑 100GB 下 P99 < 1µs 的定位与 < 1ms 的单步编辑（00 §7）。
- 叶 64 × 32B = 2KB 连续内存，区间遍历是顺序访问而非指针追逐，直接服务 16ms 滚动帧预算。
- **确定性**：同一编辑序列必产生同一棵树，快照等价性、撤销折叠、fuzz 复现与 property test 都靠这一点（见 04 §9.2）。
- 可平滑演进到多版本 buffer 分叉（见 04 §10 Q8）。

**代价**
- 是候选里实现复杂度最高的一个（900~1300 行），需要 split/merge/rebalance 全套。
- 叶子碎片化是唯一真天敌：每叶只剩 1~2 个 piece 时树高退化为 log₂N，须靠装载率下限、强制相邻合并、局部 defrag 三重防御（见 04 §3.1 论证 3）。
- 复杂度税是持续的测试成本：每步 `check_invariants()` 与 property test 不可省。

**何时应重新考虑**
- 真实负载下碎片化压不住，且 §3.3 的最小 placeholder 规则已被证明失效。
- 出现"同一 Buffer 大量并发历史分支"的需求（假设性编辑树），届时 RRB 类结构更合适。
- 若实测 piece 数长期 < 10³，容器复杂度不再值得。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| implicit treap | 随机优先级破坏"同序列同树"，快照等价性与 fuzz 复现失去确定性基础；每层一次 cache miss，20 层 ≈ 1.5µs |
| rope / AVL | 为文本设计、叶按字符计，对"100GB placeholder + 8 字节 literal"的极不均分布退化；旋转分支多、深度 log₂N ≈ 20 |
| `Vec<Piece>` 分段表 | 插删 O(N)：10 万片 × 32B = 3.2MB 描述子，文件头附近编辑平均 memmove 1.6MB；1000 次/分 ⇒ 1.6GB/s 纯带宽浪费 |
| skip list | 概率性最坏情况 + 24B/片指针开销，缓存不友好，且无确定性收益 |
| RRB 持久化向量 | 为多版本分叉设计，节点带大小表开销高；本系统只需单链 COW |
| 整文件 `Vec<u8>` / gap buffer | 100GB 直接死；gap buffer 只对光标邻近编辑有效，且无法表达 placeholder（见 04 §1.3） |

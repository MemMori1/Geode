# 0017 — journal 不持久化撤销栈，由 journal 重建

## 状态

已接受（2026-11-08）

## 背景

崩溃恢复的唯一真相来源是 journal：它只记 `EditOp` 序列、与 piece table 实现解耦、单条 < 1KB，触发点为空闲 **800ms** / 累计 **64 次编辑** / Ctrl+S 前强制 flush；`journal_fsync_ms = 1000`（语义"最多丢 1 秒编辑"），因为逐条 fsync 在机械盘上要 5~10ms 会卡编辑。撤销历史在内存里受 `undo_memory_limit_mb = 256` 约束（见 04 §8、17 §4.5）。持久化撤销栈需要把每步的 COW 快照/大操作全文及游标状态一并落盘，数据量与语义都远超 journal。

## 决策

**默认不持久化撤销栈**；崩溃后由 journal 重建"到崩溃点的状态"，不重建完整撤销栈，并在撤销栈底压入 `RecoveredFromJournal(count)` 标记。

## 后果

**好处**
- 语义可预测：撤销栈从恢复点开始，用户不会遇到"能撤销到崩溃前 50 步"这种半真半假的预期。
- journal 保持极简（只有 `EditOp` 序列），单条 < 1KB、无需与撤销的 COW 快照纠缠，也让"journal 与 piece table 实现解耦"这条约束成立。
- 落盘量小，才能在 800ms 空闲/64 次编辑的节奏下写而不卡；`journal_fsync_ms = 1000` 的取舍才有意义。
- "恢复动作本身可撤销"用一条栈底标记表达，既满足"后悔恢复"又不引入历史回放。

**代价**
- 崩溃后无法"撤销回崩溃前的编辑"，只能前滚到崩溃点再手动改回；对依赖长撤销链的用户是体验落差。
- 需要一条明确的 UI 提示（恢复对话框非模态）说明撤销栈被重置。
- `editor.persist_undo` 配置项被保留但 **M1 不实现**——一个长期未实现的可配置项本身是文档负担。

**待澄清**
- 17 §4.8 未说明 `RecoveredFromJournal(count)` 在 UI 上如何呈现（是否可在撤销链里显示为一条可查看的条目），也未给 `persist_undo` 的实现里程碑。

**何时应重新考虑**
- 若用户研究显示"崩溃后要能撤销回去"是高频抱怨，且 COW 快照可按需惰性落盘的方案被验证可行。
- 若 journal 改为记录完整操作语义（含选择/视图状态），可顺带支撑撤销栈重建。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 持久化完整撤销栈 | 语义混乱（用户预期"能撤销到崩溃前 50 步"），且数据量远大于 journal、需与 COW 快照耦合，破坏"journal 只记 EditOp"的解耦约束（见 17 §4.8） |
| 崩溃后直接丢弃未保存编辑 | 与"journal 是未保存编辑唯一真相来源"冲突，也是最容易流失用户信任的行为 |
| 自动删除失败恢复的 journal | 明确禁止：恢复失败绝不自动删除 journal，须保留 + 报路径 + 可导出；丢弃也要先移 `.trash` 留 7 天（见 17 §1） |
| 用嵌入式数据库存 journal 与撤销 | 会让"内容/项目目录进 git"失败；单文件 TOML + 追加式 journal 已够（见 17 §1） |

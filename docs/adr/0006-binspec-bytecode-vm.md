# 0006 — BinSpec 编译到字节码，由 VM 执行

## 状态

已接受（2026-11-08）

## 背景

BinSpec 是 Geode 自带的领域语言（`.bspec`），其源码有两条来源：人工编写与 AI 生成。这意味着执行侧必须同时满足：**不可信输入**、**每步可计量**、**随时可取消**、**可单步调试**。预算上限是硬数字：`steps` 默认 50_000_000、`wall_time` 默认 5s、变量 1_000_000、嵌套/递归 256 层、输出 64MB；超预算报 `E2001` 并附带已解析的部分结果。性能预算是 1000 行模板编译 < 20ms、10MB 文件 + 中等模板执行 < 100ms（见 00 §7、02 §7.2）。

## 决策

BinSpec 编译流水线固定为 `source → lexer → parser → AST → 语义检查 → 字节码 → VM 执行`，**不做 AST 树遍历解释**。

## 后果

**好处**
- **指令计数即预算**：`steps += 1` 粒度精确、实现简单，且是沙箱的唯一保障（见 02 §7.2）。
- **取消延迟 < 1µs**：Esc / 编辑 / 换文件在当前指令边界即可中断，而不是等一个 AST 节点跑完。
- 栈深限制天然由 VM 帧栈控制，不需要额外的递归检测。
- 单步调试、断点、覆盖率（哪些字段被读过）都是字节码层面的廉价操作，直接服务 AI 修复闭环的诊断质量（见 03 §2）。
- 编译期就能报出类型/语法错误（E4xxx），把 AI 的失败前移到"不执行也能判错"。

**代价**
- 多一层编译产物与指令集设计成本，调试时需要"源码行 ↔ pc"映射表。
- 字节码版本的兼容性成为长期负担：模板缓存与 `.geopkg` 里的编译产物都必须带版本号。
- 编译器是最难 fuzz 的部分（六个 fuzz 入口之一，见 18 §7），且必须保证"预算耗尽被正确报告"而非挂死。

**待澄清**
- 02 §7 未说明字节码格式是否稳定到可跨版本缓存；若模板库要预编译分发，需要明确字节码版本策略与失效规则。

**何时应重新考虑**
- 若引入 JIT/AOT（例如把热点模板编译成本地码），预算与取消语义需要重新定义。
- 若字节码复杂度开始侵蚀"编译 < 20ms"预算。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| AST 树遍历解释 | 预算粒度只能落在节点级，粒度粗；取消要等节点返回；栈深靠递归自然增长，无法按帧限制（见 02 §7.1） |
| 直接翻译成 Rust 并 `cargo build` | 编译延迟以秒计，与"编译 < 20ms"和"AI 3 轮修复"的交互节奏冲突；且引入不可信代码编译这一更大风险面 |
| 用现成脚本 VM（如 WASM/lua） | 数据模型与 `ByteRange`、`unresolvable`、`#[assert]` 等语义强绑定，桥接层比自建 VM 更贵 |
| 树遍历 + 外部步数计数器 | 仍是树遍历，取消与栈深两个问题都还在；计数器只能解决预算一项 |

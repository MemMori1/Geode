# 0014 — YARA 引擎采用 yara-x

## 状态

已接受（2026-11-08）

## 背景

YARA 的输入是**不可信的用户规则**，还要扫描不可信的 100GB 级数据，二者叠加使"内存安全 + 无全局状态"成为硬要求。性能目标：1GB 单线程扫描 < 30s（≥ 35MB/s）、内存增量 < 200MB、100GB 时内存恒定（见 12 §1）。同时 Y8 要求"只支持已实现的子集，未支持特性在编译期明确报错"，因此需要一个能做逐文件编译、单条失败不互相牵连的编译器。libyara 是 C 4.5，带 `yr_initialize()` 全局状态，FFI 包装是主要 bug 源。

## 决策

采用 **yara-x** 作为唯一实现，并抽象为 `trait YaraEngine` 以便必要时回退。

## 后果

**好处**
- 规则处理全程在 Rust 内存安全边界内，无需为不可信规则维护 `unsafe` FFI 面；无全局初始化状态，测试与并发扫描干净（每个扫描器自带状态）。
- 流式 API 原生支持大文件：`Compiler::add_source` → `Rules`，`Scanner::scan_block(&mut self, block)` 的跨块匹配状态由引擎维护；配合 1MiB/块 + 协作取消即可覆盖 100GB 且内存恒定。
- 少一个 C 依赖，直接服务工程目标 E1（默认构建零 C/C++ 依赖，见 18 §1）。
- 逐文件编译与单条失败隔离天然契合规则的四档 namespace（builtin / user.<目录> / pack.<id> / adhoc）。

**代价**
- yara-x 生态年轻（2023 起），部分模块（cuckoo、部分 dotnet、magic 相关）未实现，v1 不支持 `include`。
- 不支持的语法必须**明确报错**而非静默降级，用户从 libyara 迁移时可能遇到"规则能用但这里编译不过"。
- 需要 `trait YaraEngine` 这层抽象为回退留口，多一层间接。

**待澄清**
- 12 §4.1 未说明 `trait YaraEngine` 的回退目标究竟是什么（是自己实现的子集引擎，还是降级到 libyara）；若回退目标含 libyara，则 E1 的"零 C 依赖"需为该路径开 feature flag 例外。

**何时应重新考虑**
- yara-x 长期缺关键模块且社区无法补齐，导致用户规则命中率显著受损。
- 若需要与上游 YARA 规则库 100% 语法兼容（含 `include`）成为产品硬要求。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| libyara（C 4.5） | ①不可信规则下内存安全与无全局状态是硬要求，`yr_initialize()` 全局状态 + `unsafe` FFI 包装是主要 bug 源；②无原生块流式，需手写 block 迭代器并在 `CALLBACK_MSG` 里自己算偏移；③多一个 C 依赖，违反 E1（见 12 §4.1） |
| 自研 YARA 子集引擎 | 规则语法与模块面远比想象大，等于重做一个 YARA；且无法复用上游规则生态 |
| 假装兼容（遇到未支持特性静默跳过） | 会让用户以为规则在保护而实际没生效，安全语义上不可接受（Y8 明确否决） |
| 只用 libyara 而不用 trait 抽象 | 把引擎选择写死在调用点，未来切换成本高 |

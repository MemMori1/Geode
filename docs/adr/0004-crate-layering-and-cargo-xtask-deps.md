# 0004 — crate 分层与单向依赖，`cargo xtask deps` 机器校验

## 状态

已接受（2026-11-08）

## 背景

全系统内部 crate 分布在 **L-1 到 L4 共 6 个层号**上，依赖只能严格下降：`L4 app → L3 ui → L2 {project, ai, content, plugin-host} → L1 {analysis, bspec, viz, migrate, proc, search, diff, disasm, yara} → L0 {buffer, provider, annot} → L-1 {core}`。同层依赖只允许在允许矩阵里显式列出，未列出即违规。硬约束：除 `geode-ui`/`app` 外任何 crate 的依赖树中不得出现 `egui*`/`wgpu`/`winit`/`arboard`/`egui_kittest`（见 00 §2、18 §3.2）。人工 review 拦不住"顺手加个依赖"，必须机器判定。

## 决策

用 `cargo xtask deps` 在本地 2s、CI 内以 `E01xx` 错误码强制校验分层，任何违规边直接构建失败。

## 后果

**好处**
- 四条规则全部机器可判：**E0101** GUI 污染（非 ui/app 依赖 GUI）、**E0102** 方向（`dep.layer >= pkg.layer`）、**E0103** 白名单（目标不在允许矩阵）、**E0104** C 依赖未走 feature flag；另有反向检查 **E0105**（以外部视角看谁把 GUI 拽进来，防传递依赖）。
- 报错格式固定为 `E01xx <pkg> -> <dep>: <一句话> (见 18-engineering-plan §3.2)`，报错本身指向修复方式。
- 层与白名单硬编码在文档表格里，改动必须改 PR 中的 18 §3.2，评审面可见。
- 支撑"默认构建零 C/C++ 依赖"（E1）与"未来可换 UI 框架而不动内核"。

**代价**
- 允许矩阵是人工维护的第二份真相，新增 crate/依赖必须先改文档再改代码，多一步流程。
- 唯一允许的例外（`--cfg test` 下 `geode-ui` 可依赖 `egui_kittest`）必须写进表格，不允许内联 `#[allow]` 绕过，仍需人守着这条。
- 规则只覆盖内部 crate 的直接/传递依赖边，语义泄漏（如 L1 里写了本该属于 L2 的策略）仍靠 review。

**何时应重新考虑**
- M6 之后若抽出 `geode-core` 供外部复用（单 workspace 变多仓库），层号体系需要重新定义。
- 若插件机制引入"插件对宿主能力的反向依赖"，需要扩表而不是改规则。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 只靠 code review | 与 06/08/13/15 曾撞错误码同源的事故模式；"顺手加个依赖"是人性的漏洞而非纪律问题 |
| 用 workspace 拆成多个仓库物理隔离 | M6 之前属非目标（见 18 §1），且会让单次重构跨仓 |
| 用 `#[deny]`/lint 内联豁免 | 内联 `#[allow]` 绕过会让规则变成"建议"，与 00 §9 的"不引入隐式全局状态"同样不可接受 |
| 只查方向不查白名单 | 通过 E0102 的"合法降层"仍可能是设计上禁止的边（如表里未列的同层依赖） |

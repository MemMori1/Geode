# 0008 — 滚动条按"比例尺"自绘，不用 `egui::ScrollArea`

## 状态

已接受（2026-11-08）

## 背景

100 GiB 按 16 字节/行 = **6,710,886,400 行**；一屏典型 52~62 行（`visible_rows = ceil(viewport_h/row_h)+1`，硬钳 < 96）。`egui::ScrollArea` 的滚动量在 **f32** 中累加，超过约 **1.6e7 px** 后单次增量小于 1 ULP，表现为"拖不动/跳格"（见 01 §4.5）。更根本的是像素分辨率：4000 px 轨道 ÷ 67 亿行 ⇒ **1 px ≈ 1.68e6 行 ≈ 26.8 MB**，任何"逐行跟手"的滚动条在语义上都是错的。滚动帧预算 < 16ms（p99 < 25ms），且跳转 100GB 需 < 5ms（见 00 §7）。

## 决策

自绘滚动条，把位置表示为 `ScrollPos { row: u64, sub: f32 }`，以"比例尺"而非"可滚列表"的交互模型实现。

## 后果

**好处**
- 精度问题被结构性地消掉：位置用 u64 行号（f64 可精确表示到 2^53 ≈ 9e15，67 亿行安全），无累加漂移。
- 交互可设计为符合比例的语义：拖拽走**跳跃预览**（顶部浮层显示目标偏移 + 该行前 8 字节 + `deepest_at` 结构路径），松手才真跳，不逐行跟手。
- 粒度档位 1x/16x/256x（双击 thumb 切换）把"微调"与"跨文件"两个量级分开；thumb 最小高 20px 保证可抓取。
- 与虚拟滚动、64KiB 块读（一次覆盖 68 屏）、settle_ms = 80 后的精修读配合，滚动期只需低精度数据。

**代价**
- 需要自己实现拖动、双击切档、中键 1:1 平移、滚轮 3 行/格（连续加速上限 30 行/格）、PageUp = `visible_rows-1`、Ctrl+Home/End 到文件首尾等全套交互与命中测试。
- 用户可能把滚动条误当"连续控件"，须用标签"`<total_rows> 行 / <total_bytes>`"明示它是比例尺。
- 每次交互都要维护"锚定光标字节的屏幕相对位置"这条不变式，测试面变大。

**何时应重新考虑**
- 若 egui 引入 u64/i64 精确滚动量并保证大偏移可用，可回收部分自绘工作。
- 若产品改为"分页/窗口化"模型（不再承诺任意位置直达），比例尺的必要性下降。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| `egui::ScrollArea` | 滚动量为 f32 累加，> ~1.6e7 px 后单次增量小于 1 ULP ⇒ 拖不动/跳格（见 01 §4.5、05 §4.2） |
| 用 f64 存滚动量并喂给 ScrollArea | f64 只解决数值精度，不解决 1 px ≈ 26.8 MB 的**像素分辨率**问题 |
| 虚拟"加长滚动区"（每行映射到固定像素） | 67 亿行 × 任意 row_h 远超 f32 表示范围，等同方案一 |
| minimap 缩略图替代滚动条 | 需要额外抽样读取与绘制预算，且不解决"如何定位到 26.8MB 粒度以下" |

# 0015 — 内容分发先上静态索引

## 状态

已接受（2026-11-08）

## 背景

内容分发的需求是"用户能发现、安装、更新、回滚包"，但 v1 的预期包量很小。服务端的真实成本不在存储而在**运维与一致性语义**：索引服务、灰度、统计、区域路由都需要持续投入，而包数量少时这些能力没有收益。可量化的规模约束：`index.json` 在 **2MB（约 5000 个包）** 以下时，一次 `GET` + 条件请求就能覆盖整个目录；包更新频率在**每周 < 30 个**时，静态文件的发布节奏足以跟上。阶段 1 的目标是**零后端成本**（只有静态文件 + 一个 CDN）。见 15 §4.2。

## 决策

阶段 1 采用**静态索引**：CI 从各内容仓库的 `manifest.toml` 反向聚合出 `index.json`，作为 GitHub Release asset 或任意 CDN 的固定路径发布；客户端条件请求 + 本地缓存 6h。

- 客户端发 `If-None-Match`/`If-Modified-Since`；本地缓存 **6h**（`expires_at` 优先），离线可用过期缓存但 UI 标"索引已过期 N 天"。
- 下载走 `cache/downloads/<sha256>.part` + Range 断点续传，校验通过才 rename。
- 阶段 2 补签名与撤回：`.geopkg` 附 `.sig`、`index.json.sig`、`revocation.json`（≤ 64KB，TTL **15 分钟**、每天至少拉一次，与索引 6h TTL 解耦）。
- 安装/更新/回滚是事务（断电注入 100 次只有"旧"或"新"两态）；激活 = 改 `state.toml` 一行指针，不移动文件。

## 后果

**好处**
- 零后端运维：没有服务可挂、没有数据库要迁移，成本只剩静态存储与 CDN 流量。
- 索引可缓存可镜像，离线与内网部署都成立，符合"包体永远走静态 CDN"的长期立场。
- 事务式安装 + 断点续传让"装到一半断电"不会留下半成品，回滚只是指针切换。
- 网络层可用阻塞 `ureq` 跑在 job 线程，不必为它引入异步运行时（与 0005 一致）。

**代价**
- 主动放弃搜索排序、下载统计、灰度渠道（只有 stable/beta 两个静态文件）、按区域路由（交给 CDN）。
- 每次内容更新都要全量重建 `index.json` 并重新发布，发布链路耦合 CI。
- 阶段 1 **不对 `index.json` 本身签名**，索引完整性依赖 HTTPS 与 CDN；恶意镜像可篡改目录（包体签名可挡住执行，但目录可被污染）。
- 过期缓存的"可用但标记过期"是刻意取舍，需要 UI 持续提示。

**待澄清**
- 15 §4.2 给了阶段 3 的信号阈值（`index.json` > 2MB、每周新增 > 30 包、Top 50 搜索词"无结果"占比 > 25%、出现付费/企业私有内容或需 < 15 分钟下架），但未说明这些信号是"任一满足即上"还是"满足两项以上"，也未给阶段 2→3 的决策责任人。

**何时应重新考虑**
- 上述任一阈值被触发（尤其"需 < 15 分钟下架"这类合规要求）。
- 即便进入阶段 3，也只把**索引与搜索**搬到服务端，包体仍走静态 CDN。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| v1 就上服务端索引 | 包量小时服务端只带来运维成本与一致性负担，换不来搜索/统计价值（见 15 §4.2） |
| 内置全量包清单（随客户端发布） | 内容更新要发新版客户端，且清单与二进制耦合 |
| 直接读各内容仓库（GitHub API 直连） | 客户端要处理多源聚合、限流与速率配额，与"零后端"目标相悖 |
| 用嵌入式数据库存索引 | 会让"内容目录进 git"失败；同理 17 §1 也否决了 sqlite |
| 阶段 2 就把包体搬上自建服务 | 静态 CDN 已能满足，自建只会增加带宽成本与可用性风险 |

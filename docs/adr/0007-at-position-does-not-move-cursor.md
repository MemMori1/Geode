# 0007 — `@` 位置声明不移动游标

## 状态

已接受（2026-11-08）

## 背景

BinSpec 的成员声明语法为 `<type> <name> [ <array> ] [ @ <offset> ] [ if <cond> ] ;`（见 02 §4.1）。`@` 用于把一个结构钉在文件指定位置，典型形态是指针数组：`u32 ptrs[256] @ 0x40;` 后跟逐个 `Item it @ ptrs[i];`，逆向一个含 256 个指针的文件。若 `@` 顺带移动读游标，这类"散布在文件各处的结构"就无法独立描述，每读一个都要手工复位。越界语义上，`@` 目标越界不是硬错误，标 `unresolvable` 后继续解析（见 02 §3.3 S1，逆向时指针经常是坏的）——这也说明 `@` 是"附加定位"而非"转移控制流"。

## 决策

规定 `@` 声明的求值等价于"在 `expr` 处读一个成员"，**读完后游标回到原处**（语义规则 S2，见 02 §4.2）。

## 后果

**好处**
- 散布结构可组合：指针数组里每一项都是独立声明，互不影响，模板可按数组下标随意重排与复用。
- 与 ImHex 行为一致，用户已有模板迁移零认知成本（见 02 §4.2）。
- 与 `<array> @ <offset>` 的写法天然协同：数组元素各自定位，不需要 `seek` 语义。
- 游标语义保持"只被顺序成员声明推进"这一条单一规则，VM 实现与单步调试的状态也简单。

**代价**
- "顺序读 + 偶尔跳转"变得啰嗦：跳转后要回到新位置继续顺序读，必须显式写 `@ $`。
- 用户从 C 风格结构体直觉出发容易误以为 `@` 会移动游标，诊断信息需要给出可操作的修复建议。
- 无法表达"在位置 X 读完后从 X 继续"的紧凑写法，模板行数略增。

**待澄清**
- 02 §10 Q1 将本条列为待定项：备选方案是提供 `seek()` 或让 `@` 移动游标，原文倾向"保持不移动（可组合性 > 简洁）"但未最终裁决。本 ADR 按原文倾向记为已接受；若后续改为移动语义，须以新 ADR 取代本篇。

**何时应重新考虑**
- 若真实模板样本里 `@ $` 的出现频率高到影响可读性（例如占成员声明数 > 20%）。
- 若引入"作用域/游标栈"等新语义，需要重新定义 `@` 与游标的关系。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| `@` 移动游标 | 指针数组场景下每个元素都要手工复位，破坏"独立描述散布结构"这一核心用法 |
| 提供 `seek(expr)` 语句 | 引入第二个能改游标的原语，语义面变大；`@ $` 已能表达同一意图（见 02 §10 Q1） |
| 两种模式并存（`@` 与 `@!`） | 同一符号两套语义，是模板迁移与 AI 生成的最大误解源 |

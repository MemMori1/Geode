# Geode ADR（架构决策记录）

本目录记录 Geode 已作出的**架构级决策**，每篇只回答一个问题：当时为什么这样选、否掉了哪些方案、以及什么条件下应该重开这个辩论（见 18 §8）。设计文档（`docs/00`~`18`）描述"现在是什么"，ADR 描述"为什么不是另一个样子"；两者冲突时以设计文档为现状基线，并应提 ADR 修订。

## 编号规则

编号 `NNNN` 四位、**只增不改**——已发布的 ADR 永不删除、永不改结论（可以修措辞）。修订即写一篇新号 ADR，并在旧文的 `## 状态` 写明 `被 NNNN 取代`，在新文的 `## 状态` 写明 `取代 NNNN`。文件名格式 `NNNN-短横线英文标题.md`，引用格式 `见 ADR-0007`。

## 状态机

| 状态 | 含义 | 允许的迁移 |
|---|---|---|
| 待定 | 已讨论、尚未裁决，或原文自述为开放问题 | → 已接受 / 已否决 |
| 已接受 | 当前实现遵循此决策 | → 已取代（新号接替） |
| 已否决 | 明确不做，理由已留档 | → 已取代（条件变化后重开，写新号） |
| 已取代 | 已有新号 ADR 接替，本文仅作历史 | 终态 |

## 何时该写 ADR

三条判据，**满足任意一条**即应写：

1. 会影响**两个以上子系统**（跨 crate 或多层）。
2. 有**真实的备选方案被否**，且否决理由不是"更简单"这种一句话能说完的。
3. 事后**一定有人会问"为什么当初不那样做"**——通常意味着重开该辩论的成本很高。

反例：局部命名、单个 crate 内部的数据结构细节、可以随时无痛替换的实现选择，都不写 ADR。

## 如何新增

1. 取下一个可用编号（`ls docs/adr/ | tail -1`，当前最大为 0018），按 `NNNN-短横线英文标题.md` 建文件。
2. 套用现有 ADR 的五节结构：`## 状态` / `## 背景`（必须含具体数字约束与 `见 NN §x.y` 引用）/ `## 决策`（一句祈使句）/ `## 后果`（好处·代价·何时应重新考虑，含糊处写 `待澄清`）/ `## 备选方案与否决理由`（表格，每条 1~2 行）。
3. 结论必须能在设计文档中找到依据；**不得在 ADR 里发明新决策**——若想法是新的，先改设计文档再写 ADR。
4. 更新本 README 的索引表与「待澄清汇总」，并在被取代的旧 ADR 的 `## 状态` 写 `被 NNNN 取代`。
5. 在 PR 中与设计文档改动同批提交（见 18 §1 E5：文档与代码不漂移）。

# S3：纯 `Painter` 能否撑住一屏 hex 网格

- 判定标准（18 §10.3 S3）：一屏 ~5000 个 quad 在 **16.6 ms**（60 fps）内完成，目标 < 8 ms。
- 结论：**通过，且余量约 20 倍**。最坏一档 15,360 个图元耗时 **0.83 ms**。

## 怎么测的

`crates/geode-ui/benches/paint.rs`（criterion），用 `egui::Context::run` 跑一帧
`CentralPanel`，在 `ui.painter()` 上画 `cols × rows` 个格子，**再把 `shapes` 交给
`ctx.tessellate`** —— 也就是说，测的是"几何生成 + 三角化"，不含 GPU 提交。

| 档位 | 格子数 | 图元数 | 中位耗时 |
|---|---:|---:|---:|
| 16×68（一屏） | 1,088 | 2,176 | **167 µs** |
| 32×90 | 2,880 | 5,760 | **356 µs** |
| 64×120（最坏） | 7,680 | 15,360 | **824 µs** |
| 文本路径 16×68 | 1,088 | 1,088 | **114 µs** |

文本路径（每格 `Painter::text`，查字形图集 + galley）反而更快，因为 `egui` 对相同
字符串缓存 galley，且图元数少一半。真实实现会更便宜：hex 列只预排版 22 个符号，
直接出 quad（05 §4.3）。

## 这个结论**没有**证明什么

1. **不含 GPU**：`wgpu` 提交、纹理上传、swapchain 都未计入。理论上 5000 quad 对任何
   2015 年后的 GPU 都是噪声，但"理论上"不等于测过——这条留给 M0 收尾的真窗口。
2. **不含布局与命中测试**：鼠标 hover/选区命中是 O(可见格) 的 CPU 工作，量级远小于
   16 ms，但也没测。
3. **字体是 egui 默认**：真实用 Sarasa Mono SC（3.4 MB），图集构建是**一次性**成本，
   首帧会更高（26 §5.1 的"首帧 <250 ms"是另一条预算）。
4. 机器是这台 Mac（Apple Silicon），不代表低端 Windows 笔记本；21 §4.2 要求基准机
   记录型号，这里先记"开发机，未锁定频"。

## 对架构的影响

- 05 §4.3 的"整帧 1 张 atlas、≤8 draw call"方案**不需要改**；
- 不需要退到 `wgpu` 自绘管线（那会引入 05 §7 里列的三个坑：图集管理、DPI 重建、文本 shaping）；
- `egui::ScrollArea` 依然禁用（那是 f32 累加问题，与本 spike 无关）。

证据可复现：`cargo bench -p geode-ui --bench paint`。

# 类 ImHex 十六进制编辑器：功能调研与技术难点

> 调研时间：2026-11
> 对标物：ImHex（C++ / ImGui / Pattern Language，GitHub 55.8k star，自有代码约 20~30 万行，含第三方依赖全仓 490 万行）

---

## 0. 结论先行

1. **ImHex 不是一个"hex 查看器"，它是"带编辑能力的二进制结构解析 IDE"**。真正的护城河是 Pattern Language（自研 DSL + 解释器 + 模板库生态），不是 hex 视图本身。hex 视图一个月就能写出可用的，Pattern Language 写了五年还在迭代。
2. **如果不做 DSL，你的产品就退化成 HxD / Hex Fiend**。这两个已经免费 + 成熟 + 跨平台，正面刚没有胜算。所以要么做 DSL，要么在别的轴上切（团队协作、云端、超大数据集、特定行业格式）。
3. **架构上唯一致命的决策是"缓冲区数据模型"**。选错了（整文件读进 `Vec<u8>`），后面插入/删除、超大文件、撤销、diff 全部要重写。正解是 piece table（分段表）或带字节计数的 B-tree。
4. **最贵的不是技术难点，是"错误体验"和"模板生态"**。用户 90% 的挫败感来自"模板跑不通、报错看不懂、不知道哪个字段错了"。这部分是纯脏活，没有技术含量但决定产品生死。

## 1. 竞品与定位

| 产品 | 平台 | 模板/解析能力 | 授权 | 值得抄的点 |
|---|---|---|---|---|
| **ImHex** | Win/mac/Linux/Web | Pattern Language（自研 C-like DSL，解释执行） | GPL-2.0 | 端到端体验最完整：模板 ↔ hex 双向高亮、数据处理器节点图、多数据源 |
| **010 Editor** | Win/mac/Linux | Binary Templates（C-like，语法最接近 C，生态最大） | 商业 $50~130 | 模板语法设计最"像 C"，学习成本最低；模板市场成熟 |
| **HxD** | Win | 无（纯手工 + 有限结构） | 免费 | 启动速度、磁盘直接编辑、极低资源占用 |
| **Hex Fiend** | macOS | 无（可插拔，靠外部） | BSD | 大文件性能标杆；B-tree 字节存储 + 只读 mmap |
| **Synalyze It!** | macOS | Grammar（自定义语法 + 十进制字段树） | 商业 | 语法编辑器 UI（不用写代码就能定义结构） |
| **Kaitai Struct** | 跨平台（Web IDE） | Kaitai DSL → 生成多语言代码 | MIT | DSL 编译成代码而不是解释；Web 可视化 |
| **Okteta** | KDE | 结构定义（类似 010 模板） | GPL | 结构视图与 hex 视图联动 |

**空档（可切入的方向）**：
- **超大/流式数据**：100GB+ 磁盘镜像、内存 dump、网络流。现有工具都会跪（要么 OOM，要么卡死）。
- **模板写起来不痛苦**：010/ImHex 都要学一门小语言。有没有"可视化定义 + 生成模板 + 双向同步"？
- **结构化 diff**：现有工具都是字节级 diff，插入一个字节后面全错位。按结构对齐的 diff 基本没人做。
- **协作 / 可复现**：把"分析过程"当 notebook 存下来（脚本 + 断言 + 注释 + 结果），团队共享。逆向团队真实痛点。
- **AI 辅助**：给它一段未知二进制，自动猜结构、生成模板初稿、解释字段。这是 2025+ 才成立的新轴，ImHex 只做了个 MCP 工具接口的雏形。

## 2. 功能清单（分层：先做什么，后做什么）

### 2.1 P0 — 内核（不做就不是 hex 编辑器）

**视图**
- 三栏布局：偏移量 | hex 字节 | 解码文本（ASCII / Latin-1 / 可选编码）
- 可配置：每行字节数（8/16/32/64）、字节分组（1/2/4/8）、偏移量进制（hex/dec/oct）、大小写
- 虚拟滚动，只渲染 viewport（100GB 文件也要 60fps）
- 光标 + 选区（字节区间 / 矩形多行 / 多区域）
- 跳转（绝对偏移、相对、从末尾、从当前 ±）
- 行内高亮：前景色规则（值域/ASCII 可见性）、背景色（选区、搜索结果、书签、结构）

**编辑**
- 覆盖模式（overwrite）：最常用，必须支持
- 插入/删除模式（insert/delete）：改变文件长度，成本高但用得上
- 无限撤销/重做
- patch 管理（已修改字节的独立列表，可回滚单个 patch）
- "未保存修改"状态、脏页标记

**搜索**
- Hex 模式（支持通配符 `??` / `?` 半字节通配）
- 字符串模式（ASCII / UTF-8 / UTF-16LE/BE，大小写敏感开关）
- 正则
- 数值模式（按类型 + 字节序 + 范围 + 是否对齐）
- 全文件 / 选区内
- 后台执行 + 进度条 + 可取消 + 结果列表虚拟化 + 结果数上限

**文件 IO**
- 打开 / 保存 / 另存为
- 超大文件（>4GB，64 位偏移，不整体载入内存）
- 拖放打开、命令行参数、最近文件
- 保存策略：临时文件 + 原子 rename（不要原地覆写，崩了就是数据全废）

**基础工具**
- 复制为（hex string / C array / Rust array / Python bytes / Base64）
- 数据检查器（Inspector）：同一段字节按 u8/i8/u16/u32/u64/f16/f32/f64/LEB128/GUID/时间戳/颜色 全部解一遍，可反写
- 哈希（CRC32/MD5/SHA-1/256/xxHash…），支持对选区算
- 字节统计（直方图、熵、文件类型识别 by magic）

### 2.2 P1 — 差异化（決定你是不是"ImHex 级"）

- **二进制模板 DSL**：见 §3.5。这是分水岭。
- **模板自动加载**：按 magic / MIME 匹配，打开文件自动跑对应模板
- **结构 ↔ hex 双向联动**：点结构字段 → hex 选中对应字节；反之亦然
- **数据处理器（Preprocessor）**：显示前对数据做变换（解密 / 解压 / XOR / 位反转 / 提取位平面），**不改源数据**，可多级串联（ImHex 用节点图）
- **多数据源**：原始磁盘/分区、进程内存、GDB 远程、SSH/SFTP 远程文件、UDP 流、base64、Intel HEX / SREC
- **Diff**：两个数据源对比，差异高亮 + 差异表 + 可跳转
- **反汇编集成**（Capstone）：指定架构/基址，代码/数据混合显示
- **YARA 扫描**：规则匹配高亮
- **书签/注释**：命名、配色、可在新标签页展开为独立视图
- **结构可视化**：把字段渲染成图片/音频/3D 模型/坐标/时间轴（ImHex 的杀手锏体验）
- **多标签 / 多工作区 / 可分离窗口 / 布局持久化**
- **主题系统**（可分享的主题文件，暗色默认）

### 2.3 P2 — 生态与长尾（可以慢慢堆，但决定留存）

- 插件系统（动态库 `.geoplug` / `.dll`，ABI 稳定）
- 内容市场/更新器：模板、库、magic 数据库、自定义编码、主题、YARA 规则一键下载
- 报表导出（Markdown / HTML，带结构树和高亮）
- 补丁导出（IPS / IPS32 / 自定义）
- 编码支持：UTF-8/16/32、ShiftJIS、GBK、Windows codepages、自定义编码表
- 工具集长尾：ASCII 表、正则替换器、表达式计算器、IEEE754 可视化、进制转换、字节交换、CRC 参数试验器、HTTP/TCP 客户端、文件分割/合并/粉碎、符号 demangle（Itanium/MSVC/Rust/D）
- 崩溃恢复（journal / 自动保存草稿）
- i18n（CJK 必须，字体要打包：中文用户量很大）
- 自动更新、代码签名、公证（Windows 上 hex 编辑器极易被误报病毒）

## 3. 技术难点（按"会不会逼你重写架构"排序）

### 3.1 数据模型 ★★★★★（唯一真正会逼你推倒重来的决策）

**朴素做法**：`Vec<u8>` 装整个文件。
- 后果：2GB 文件直接吃掉 2GB 内存；插入一个字节 = memmove 整个后半段；撤销 = 复制整文件。
- 只在"永远只读 + < 200MB"场景成立。

**业界正解（Simon Tatham 的 *An Efficient Data Structure For A Hex Editor*，Hex Fiend 同路线）**：

```
Piece Table / 计数型 B-tree
  节点元素 = byte block，两种：
    - Literal block : 实际字节（新建/粘贴的数据）
    - Placeholder   : (source, offset, len) — 指向原文件的窗口，不占内存
  每个节点额外字段 = 子树总字节数
```

由此得到的性质：

| 操作 | 复杂度 |
|---|---|
| 定位第 N 个字节 | O(log N)（靠字节计数下钻，不需要排序键） |
| 插入/删除 1 字节 | O(log N) |
| 剪切/粘贴任意大块 | O(log N)（split + join，不 memcpy） |
| 复制大块（COW 引用计数） | O(1) |
| 撤销（存整棵树的 clone） | O(1) 每步，内存与"实际改动量"成正比 |
| 打开文件 | O(1) — 树里只有一个 placeholder |
| 搜索 / 保存 | O(N)（无法避免） |

**内存只与"改动量"成正比**，这是支持 100GB 文件的关键。

**必须提前处理的坑**：
1. **mmap 的文件被外部截断 → SIGBUS / 进程直接死**。要么全局捕获，要么打开后持有 fd 并检测 `st_size` 变化，要么干脆不用 mmap 用 `pread` + LRU 页缓存。
2. **Windows 上无法 truncate 已被映射的文件**。保存必须写临时文件 + rename。
3. **保存 = 展开 piece table 顺序写盘**，中间失败要有回滚，绝不能在原文件上就地写。
4. **Placeholder 块最小尺寸约束**：否则会出现"1 字节 literal 与 1 字节 placeholder 交替"的病态结构，空间开销爆炸（Tatham 文章 §8 末尾专门讲了这个，别重复踩）。
5. **指针/偏移的位宽**：全程 `u64`，别用 `usize` 也别用 `long`（Windows 上 long 是 32 位）。
6. **插入模式 vs 覆盖模式的语义分离**。二者的撤销语义、选区语义、与模板联动语义都不一样。很多工具只做覆盖模式就是为省这个麻烦。

**建议**：动手前先写 3 个 RFC：（a）块存储与 COW 语义；（b）编辑操作 → 撤销记录 的映射；（c）保存事务。这三份定了，后面所有功能都只是加法。

### 3.2 渲染与表格虚拟化 ★★★★

**核心约束**：一个 32 列的视图，屏幕上一屏约 60 行 ≈ 1920 字节单元格。必须在 16ms 内完成布局 + 绘制，且与文件大小无关。

要点：
- **只渲染 viewport**：用 clipper / 行区间计算，`first_row = scroll / row_height`，绘制 `[first_row, first_row + visible_rows]`。
- **偏移量宽度动态化**：文件越大偏移列越宽（4GB 需 8 位 hex + 前缀），要按文件大小自适应，否则列错位。
- **等宽字体的字符宽度必须实测**：不要假设 `advance == font_size * 0.6`。用字体度量（或用固定格宽逐字绘制）。否则高 DPI / 不同字体下会错位。
- **CJK / 非等宽 fallback 是地雷**：默认 UI 字体缺 CJK 会 fallback，fallback 字体宽度不同 → 整个 ascii 列歪掉。hex 视图必须绑定"纯等宽、无 CJK"专用字体（如 JetBrains Mono / Cascadia Mono），UI 文字另用一套。
- **高亮属性的组织**：别在每帧重算。维护分层的"属性区间表"：
  - L0 值域规则（<0x20 显示红、可打印绿…）
  - L1 搜索结果
  - L2 模板结构嵌套（深度 → 背景色调）
  - L3 选区 / 光标行
  按区间查询（区间树或简单的分段有序数组），一个字节最终属性 = 按优先级合成。
- **Web 前端不要用 DOM 网格**：每字节一个 `<span>` = 60 行 × 32 列 × 2 视图 = 近 4000 节点，滚动就崩。必须 canvas / WebGL 自绘。
- **字形缓存**：ImGui 自带 atlas；如果用 Skia/Web，也要自己缓存 shaper 结果（每行只做一次 shaping，缓存到行号）。
- **滚动条与"无穷文件"**：滚动条 thumb 大小按文件大小算，但要防止超过浮点精度（`f32` 在 >16M 时精度不足，一律 `f64` 或整数运算）。

---

### 3.3 编码与列对齐 ★★★

棘手之处在于 hex 视图是**面向字节**的，而"显示文本"列是**面向字符**的：

- UTF-8 多字节字符横跨 2~4 个 hex 单元格。选中 / 光标 / 高亮都按字节，但视觉块要合并。
- 建议：内部一律 byte-oriented；维护 `byte_offset ↔ display_cell` 双向映射表，只在需要时（渲染可见行、鼠标命中测试）计算。
- "按 UTF-16 解码整个文件显示"这种视图不是拉伸字符，而是**重排列**（2 字节一列），属于独立视图模式，别硬塞进同一个布局。
- 无效序列的显示策略要定死（`·` / `?` / 原始 hex），不同工具做法不同，用户会感知到。
- 大小端在"显示文本"列不做处理，但在 Inspector 和 DSL 里必须处理。

---

### 3.4 搜索 ★★★

- **简单 hex/字符串搜索**：Boyer–Moore–Horspool 或 `memchr` + 首字节 SIMD 跳转，1GB 文件亚秒级可达。
- **通配符 hex 模式**（`48 8B ?? 05`）：无法用 BMH。退化为 SIMD 化的"首字节定位 + 定长比较 + 掩码比较"。
- **正则**：跨编码的正则才是真难点。UTF-16 上跑正则要先把数据转 UTF-8（内存爆炸）或用专门的 UTF-16 引擎。可行做法：分块流式解码 + 块边界重叠（重叠长度 = 正则最大可能跨度），并明确告知用户"跨块边界的匹配可能漏"。
- **必须异步**：worker 线程 + `AtomicBool` 取消 + 进度回调。搜索过程中用户还能滚动、切换文件。
- **结果失效**：编辑后结果必须标记 stale 或自动重跑。维护一个"数据版本号"，搜索结果显示时校验。

---

### 3.5 二进制模板 DSL ★★★★★（最难，也是全部价值所在）

这是 ImHex / 010 Editor 的真正产品。拆开有 6 个子难题：

#### (a) 语言设计
必须覆盖：
- 基本类型（u8..u64、s8..s64、f16/32/64、char、char16、bool、padding、auto-sized 整数）
- 复合类型：struct、union、enum、bitfield、array（定长/变长/不定长/无界）
- 字节序：全局 pragma + 单类型前缀 `be u32` / `le u32`
- 控制流：if/else、match、while（读变长数组）、for、函数、递归
- 指针：`u32 *p : u32;`（先读指针值，再解引用到该偏移）
- 位置声明：`MyStruct s @ 0x100;`、`s @ $;`（当前位置）、数组 `@ 0x100 while(...)`
- 属性/注解：`#[color("red")]`、`#[format("x")]`、`#[hex::visualize("image")]`、`#[comment]`、`#[no_unique_address]`
- 标准库（`std::mem`、`std::string`、`std::core`…）+ 用户 include

**语法取向的关键选择**：010 的语法"更像 C"，学习成本最低（这是它商业上赢的原因之一）。ImHex 的 PL 引入了 `@` 定位、`while` 数组、`#[...]` 属性，表达力更强但更怪。**如果从零做，建议语法尽量贴近 C，把特殊能力收敛到少量扩展点。**

#### (b) 编译器
`lexer → parser → AST → 语义检查（类型/作用域/常量折叠）→ 执行`
- 不要做 JIT（沙箱 + 可中断 + 跨平台成本太高）。
- 执行模型是 **offset-driven 的树遍历解释**：给定一个起始偏移，按声明顺序依次读字段，边读边维护"当前位置"。这和普通语言的执行模型有本质差异（读字段是有副作用的、依赖输入流的），设计时要想清楚。
- 需要显式"变量表"：每个已解析变量 → (name, type, offset, size, value, parent)。
- 还要支持 **模板内部触发可视化**（回调宿主程序渲染图片/音频/3D）。

#### (c) 沙箱与安全（最容易被忽略，但上线必炸）
用户脚本 = 不可信代码。必须内置：
- 指令预算（如 10M 步上限）
- 时间预算（如 5s 上限，可配置）
- 栈深上限（防递归爆栈）
- 内存上限（变量数量 / 数组元素数）
- 所有读取自动裁剪到文件边界（越界读返回错误而不是崩）
- 可随时取消（用户按 Esc / 编辑了新数据 / 换了文件）
没有这套，一个 `while(true)` 的模板就能让整个 IDE 假死。

#### (d) 错误体验（决定用户是否留下来）
- 报错必须带：**字节偏移 + 期望类型 + 实际读到的字节 + 语法位置（行列）+ 调用栈**
- hex 视图里要标出"出错的那个字节"，并且颜色可辨
- 模板作者调试时要能 `print` / `assert` / 单步
- 常见错误要给"人话"提示（"在 0x1A2 处期望 4 字节 u32，但只剩 2 字节，可能这个数组长度字段不包含尾部 padding"）
- **这块是纯脏活，但 ImHex 的 issue 区里一半的抱怨都在这里。**

#### (e) 增量重解析
100MB 文件 + 300 行模板 = 每次编辑重跑全量太慢。
- 按顶层 pattern 分片（`X @ 0x100;` 与 `Y @ 0x8000;` 独立）
- 记录每片的 dirty 字节范围，只重算相交的片
- 编辑导致长度变化（insert 模式）时，所有后续片全部失效 → 此时要么全量、要么明确提示

#### (f) 模板生态（长期运营成本，不是一次性开发）
- ImHex 的 `ImHex-Patterns` 仓库有数百个模板 + magic 自动匹配数据库
- 这是日积月累的社区工作，不写代码也得有人做
- 模式：一个模板 = 一个文件 + 一段 magic + MIME + 说明 + 测试样本

**如果不做 DSL 的替代路线**（要清楚代价）：
- 集成 Kaitai Struct：能生成代码，但**拿不到"边改边看"的实时体验**，也无法把字段映射回 hex 视图做高亮。体验会掉一个档。
- 只做"手动 bookmark + 注释 + Inspector"：那就是 HxD，产品定位完全不同。

### 3.6 Diff ★★★

- **不能用全量 Myers**：O(N·M) 对 100MB 文件直接爆炸。
- 现实做法：固定块（4~8KB）滚动哈希 → 找出相同的块锚点 → 只对锚点之间的差异区做精细 diff（Myers 或 patience diff）。
- **真正的难点是"对齐显示"**：hex 视图并排显示两份数据时，插入一个字节后所有偏移错位。有两种策略：
  - 按偏移并排（简单，但插入后全红）
  - 按 diff 锚点分段并排，段内偏移映射（体验好，实现复杂，需要维护 offset↔offset 映射函数)
- 参考实现：`rsync` 的 rolling checksum、`bsdiff`、Git 的 `histogram` diff。

---

### 3.7 数据源抽象 ★★★

统一接口：

```
trait Provider {
    fn size(&self) -> Option<u64>;     // 流式源可能未知
    fn read(&self, off: u64, buf: &mut [u8]) -> Result<usize>;
    fn write(&mut self, off: u64, data: &[u8]) -> Result<()>;  // 可选
    fn is_writable(&self) -> bool;
}
```

要覆盖的实现：LocalFile(mmap)、LocalFile(pread)、BlockDevice(`/dev/sdX` / `\\.\PhysicalDrive0`)、ProcessMemory(`/proc/pid/mem` / `ReadProcessMemory`)、GDB remote、SSH/SFTP、UDP 流、Base64 解码流、Intel HEX/SREC。

坑：
- 平台权限：Windows 上打开物理磁盘需要管理员；macOS 上 `/dev/rdisk` 需要 SIP 权限。
- 非 seekable 流（UDP/串口）：要"边收边追加 + 环形缓冲上限"，且偏移是"自连接起算的字节数"。
- 进程内存：地址空间是稀疏的（大量未映射区），读取必须捕获失败并标记"不可读区域"，UI 上要显示空洞。
- 内存里的 `Provider` 生命周期与 mmap 生命周期绑定，Rust 里要用 `Arc` + 自引用结构或 `owning_ref`。

---

### 3.8 插件系统与 ABI ★★★

- 动态库插件要求 **ABI 绝对稳定**：不能暴露 `std::string` / `std::vector` / 模板类型（编译器/STL 版本一变就崩）。用 C ABI + 不透明句柄 + 版本号校验。
- 插件要能注册：新数据源、新模板函数、新可视化器、新处理器节点、新工具视图、新主题、新列类型。
- 插件加载失败必须优雅降级（不能让一个坏插件让 IDE 起不来）。
- Rust 生态里等价物：`abi_stable` crate，或干脆 WASM 插件（安全性好、跨架构，代价是性能和数据拷贝）。

---

### 3.9 工程化脏活（不性感但必做）

- **撤销栈内存上限**：编辑 100 万次后撤销栈能吃掉几 GB。要按字节数限额 + 快照压缩。
- **崩溃恢复**：编辑中的未保存数据必须落盘（journal），重启后能恢复。
- **文件关联 / 拖放 / 最近文件 / 多标签 / 布局持久化 / 断点窗口位置恢复**。
- **CJK 字体打包 + i18n**：中文用户量大，字体文件几十 MB，要子集化。
- **签名与公证**：Windows 上 hex 编辑器被 Defender/杀软误报是常态（它做的是"修改其他程序"的事）。必须有代码签名 + 白名单申诉流程。
- **自动更新 + 崩溃上报**。
- **基准测试基线**：把"打开 4GB < 200ms / 滚动 60fps / 搜索 1GB < 1s / 模板解析 10MB < 100ms"写成 CI 里的 benchmark，否则性能会静默退化。

## 4. 容易被低估的 12 个坑

1. mmap 的文件被外部改小 → SIGBUS 崩进程。
2. Windows 上映射中的文件不能 truncate → 保存必须走临时文件。
3. 偏移量列宽随文件大小变化 → 静态布局会错位。
4. 等宽字体度量假设 → 高 DPI 下 ascii 列歪。
5. 页面滚动条用 `f32` → 大文件拖不动 / 精度跳变。
6. 插入模式下，所有"已解析位置"全部失效 → 模板、书签、搜索结果需要版本失效机制。
7. 通配符 hex 搜索 + 正则搜索的算法完全不同，别指望一个引擎全包。
8. UTF-16 正则搜索需要专门引擎，或者接受"可能漏匹配"。
9. 模板里的 `while(true)` 能让 IDE 假死 → 必须有指令预算。
10. 插件暴露 STL 类型 → 换编译器就崩。
11. 撤销栈无上限 → 大文件编辑久了 OOM。
12. 杀软误报 → 用户装不上，差评。

## 5. 技术选型建议

### 语言

| | Rust | C++ |
|---|---|---|
| 内存安全（处理不可信输入 + 插件） | ★★★★★（这是 hex 工具的核心风险面） | ★★ |
| GUI 生态成熟度 | ★★★（egui / iced / Slint / Tauri） | ★★★★★（Qt / ImGui 极成熟） |
| 大文件 / mmap / unsafe 边界 | 好（`memmap2`，边界清晰可控） | 直接 |
| 插件 ABI | 需 `abi_stable` 或 WASM | 直接 C ABI（但 C++ 侧仍是雷区） |
| 招人 / 社区贡献 | 好 | 好 |
| 现成参考代码 | 少 | ImHex / Hex Fiend 可读 |

**倾向 Rust**：解析不可信二进制 + 运行用户脚本，这两个场景是 C++ 的死亡地带（每年都有工具被恶意文件打穿）。Rust 把 unsafe 收敛到 mmap 那一小块，性价比极高。

### GUI 框架

| 方案 | 优势 | 劣势 |
|---|---|---|
| **egui**（Rust 立即模式） | 出原型最快，自绘，虚拟化容易，跨平台一致 | 表格/文本选择交互要自己写；CJK 字体需手动加载；无原生控件观感 |
| **iced / Slint** | 保留式，架构更清晰 | hex 视图这种自定义自绘场景收益不大 |
| **Qt6 (QWidget 自绘)** | 成熟、原生观感、Hex 视图用 `QAbstractScrollArea` 自绘很顺 | 授权（LGPL 动态链接）/ 包体积 |
| **Tauri + Canvas/WebGL 前端** | UI 迭代快、主题好看、Web 版直接复用 | hex 视图必须 canvas 自绘；大文件 IPC 要设计好（不要让前端拿全量数据） |
| **Flutter** | 一套代码全平台 | 桌面生态弱，文本选择/输入法在桌面端仍有坑 |

**建议**：核心（数据模型 / DSL / 搜索 / Provider）做成**独立 Rust crate，与 UI 完全解耦**。UI 先用 egui 快速验证，如果后期要更好看再换 Tauri/Qt，核心不用动。这个解耦是唯一不能省的架构投资。

### 关键依赖
- mmap：`memmap2`
- 哈希：`sha2` / `md-5` / `crc32fast` / `xxhash-rust`
- 正则：`regex`（字节模式）+ 自研 UTF-16 路径
- 反汇编：`capstone` bindings
- YARA：`yara-x`（Rust 原生重写版，比 C 版好用）
- 文件类型识别：`infer` 或移植 libmagic
- 编码：`encoding_rs`
- 符号 demangle：`rustc-demangle` / `cpp_demangle`
